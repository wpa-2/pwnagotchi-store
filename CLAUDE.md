# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

PwnStore is an unofficial plugin store/package-manager ecosystem for Pwnagotchi devices. It has no
build step, no test suite, and no package manifest — it's a handful of standalone Python scripts and
static HTML pages that get deployed by being fetched raw over HTTP (from GitHub raw / this repo's
Pages/CNAME site) directly onto a Pwnagotchi (Raspberry Pi) or opened in a browser.

## Components (each is independent, no shared imports between them)

- **`pwnstore.py`** — Standalone CLI, installed on the Pwnagotchi itself via `wget` to
  `/usr/local/bin/pwnstore`. Subcommands (`list`, `search`, `info`, `install`, `uninstall`, `update`,
  `upgrade`, `sources`) are wired up via `argparse` subparsers in `main()`. Talks to the registry at
  `DEFAULT_REGISTRY` (this repo's `plugins.json`, raw), unless overridden by `main.pwnstore_url` in
  `/etc/pwnagotchi/config.toml`. Installs plugins into whatever `custom_plugins` is configured to in
  `config.toml` (see `get_custom_plugin_dir()`), falling back to `DEFAULT_CUSTOM_PLUGIN_DIR`.
- **`pwnstore_ui.py`** — A Pwnagotchi plugin (`class PwnStoreUI(plugins.Plugin)`) that itself gets
  installed as a custom plugin and serves a mobile-friendly web UI via Pwnagotchi's `on_webhook`
  mechanism at `/plugins/pwnstore_ui/`. All HTML/CSS/JS is inlined as Python strings (no separate
  frontend build). State-changing routes (`api/install`, `api/uninstall`, `api/configure`,
  `api/restart`) require POST + a per-process CSRF token (`X-CSRFToken` header) minted in
  `_render_store()` — read-only routes rely solely on Pwnagotchi's basic auth. `pwnstore.py` and
  `pwnstore_ui.py` intentionally duplicate small pieces of logic (`is_safe_name`, version compare,
  custom-plugin-dir resolution) since they run as separate processes/contexts — keep both in sync
  when fixing bugs in shared logic since there's no shared module.
- **`builder.py`** — CI-only registry generator, not shipped to end users. Reads `repos.txt` (one
  GitHub raw `.py` URL or `.zip` archive URL per line), downloads/extracts each, parses
  `__version__`/`__author__`/`__description__` out of the plugin source via regex (handles string
  literals, variable references, and parenthesized multi-line strings), auto-categorizes plugins by
  keyword scoring (`KEYWORDS` dict) into GPS/Social/Display/Attack/Hardware/System, dedupes by
  name+highest-version, and writes the sorted result to `plugins.json`. Runs via
  `.github/workflows/update.yml` (daily cron + on push to `repos.txt`/`builder.py`), which also
  validates the output has ≥10 entries before committing.
- **`index.html`** — Static plugin gallery (fetches `plugins.json` directly, no backend), deployed via
  the CNAME to pwnstore.org.
- **`troubleshoot.html`** — Static decision-tree troubleshooting wizard (all Q&A data is inline JS).
- **`pwnconfig.html`** — Static `config.toml` builder using React + Babel + Tailwind loaded from CDN
  (`<script type="text/babel">`, no build step). Pulls the canonical defaults/plugin list from
  Pwnagotchi upstream's `defaults.toml` (`GITHUB_RAW_URL`), not from this repo's own registry.
- **`socials.html`** — Static links page.
- **`plugins.json`** — Generated artifact (by `builder.py`); don't hand-edit, edit `repos.txt` instead.
- **`.github/workflows/update.yml`** — Rebuilds `plugins.json`.
- **`.github/workflows/update-badges.yml`** — Syncs README version badges from `__version__` in
  `pwnstore.py`/`pwnstore_ui.py` on every push that touches those files.

## Adding/changing a plugin source

Don't edit `plugins.json` directly — it's regenerated by CI. Add a raw `.py` URL or `.zip` archive URL
to `repos.txt` (see `docs/CONTRIBUTING.md` for the exact accepted URL shapes); the registry rebuilds
on push or the next daily cron.

## Running things locally

No test suite or build tooling exists. To sanity check a `builder.py` change:

```bash
pip install requests
python3 builder.py     # regenerates plugins.json from repos.txt
```

`pwnstore.py` and `pwnstore_ui.py` can only be meaningfully exercised on/against a real Pwnagotchi
(they read `/etc/pwnagotchi/config.toml`, require `pwnagotchi.plugins`/root for installs, etc.) —
review code changes carefully rather than expecting to run them locally.

## Security-sensitive conventions to preserve

- Plugin names from user input or the registry must pass `is_safe_name()`
  (`^[a-zA-Z0-9_-]+$`) before being used in filesystem paths, everywhere this pattern exists
  (`pwnstore.py`, `pwnstore_ui.py`, `builder.py`'s zip-path handling) — this is the path-traversal
  guard.
- `path_inside_zip` from the registry is validated against `..` and leading `/` before extraction
  (see `_install_plugin_by_name` in `pwnstore.py`).
- Downloaded content is sanity-checked to reject HTML error pages masquerading as plugin code
  (`looks_like_plugin()` in `builder.py`; inline check in `pwnstore.py`).
- `pwnstore_ui.py`'s state-changing webhook routes require both POST and a matching CSRF token
  (`_csrf_valid`) — read-only routes rely on Pwnagotchi's basic auth alone. Keep new state-changing
  routes under the same POST+CSRF check in `on_webhook`.
- `builder.py` caps ZIP downloads at `MAX_ZIP_SIZE` (50MB) via streaming, to avoid OOM from a
  malicious/huge repo archive.
- User-sourced content rendered into `index.html`/`troubleshoot.html` is escaped (`escHtml`/
  `escapeHtml`) before insertion — preserve this when touching rendering code.

## Versioning

`pwnstore.py` and `pwnstore_ui.py` each carry their own `__version__` (CLI and Web UI version, shown
in README badges). Bump the relevant one when making a user-facing change to that component; the
badge-update workflow syncs README automatically from these on push.
